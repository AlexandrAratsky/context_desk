# Context Desk

> Local context manager for AI coding agents

## Software Requirements Specification (SRS)

Версия: 1.0 (MVP)

---

# Часть 1. Концепция проекта

## 1.1 Назначение проекта

**Context Desk** — локальное настольное веб-приложение для централизованного хранения, редактирования и распространения AI-контекста, используемого современными AI coding agents в средах разработки.

Под AI-контекстом понимаются:
- Skills — специализированные инструкции или экспертные материалы;
- Rules — правила поведения и ограничения для AI-агентов;
- Prompts — готовые шаблоны запросов, используемые разработчиком вручную или через MCP.

Основная задача приложения — предоставить **единый источник истины** (Single Source of Truth), из которого контекстные объекты могут экспортироваться в различные IDE и AI-плагины в их нативных форматах.

Приложение работает полностью локально, не требует регистрации, облачных сервисов или подключения к Интернету (за исключением установки зависимостей).

---

## 1.2 Проблема

Сегодня практически каждая IDE и AI-плагин использует собственный формат хранения AI-контекста.

Например:
- Zed использует Skills и Instructions.
- Kilo Code использует Skills и Rules.
- Explyt использует Skills и Rules.
- Другие IDE используют собственные механизмы.

В результате разработчик сталкивается с рядом проблем.

### Дублирование информации

Одна и та же инструкция приходится хранить в нескольких местах.
После изменения необходимо вручную обновить несколько копий.
Это приводит к рассинхронизации.

---

### Разные форматы

Каждая IDE предъявляет собственные требования:
- расположение файлов;
- структура каталогов;
- обязательные поля metadata;
- дополнительные служебные параметры.

Даже если содержимое совпадает, формат хранения отличается.

---

### Отсутствие централизованного управления контекстом

Не существует единого интерфейса, позволяющего:
- увидеть все имеющиеся контекстные объекты;
- быстро найти нужное;
- изменить один раз и распространить изменения;
- понять, какие IDE используют конкретный объект контекста.
    

---

### Ограничения MCP

Протокол MCP хорошо подходит для динамической публикации Prompts, Tools и Resources.

Однако большинство современных IDE:
- не умеют хранить Skills через MCP;
- используют собственные локальные механизмы;
- не отображают Skills как MCP-объекты.
    

Поэтому MCP не может заменить файловую синхронизацию.

---

## 1.3 Цель проекта

Создать единое локальное приложение, которое позволит:
- хранить весь AI-контекст в одном месте;
- удобно редактировать контекстные объекты;
- экспортировать их в различные IDE;
- предоставить библиотеку Prompts;
- при необходимости публиковать Prompts через встроенный MCP Server.
    

При этом приложение **не должно становиться полноценной системой управления знаниями (Knowledge Management System)**.
Основная задача — максимально упростить сопровождение рабочего AI-контекста разработчика.

---

## 1.4 Основные принципы

При проектировании системы необходимо придерживаться следующих принципов.

### Single Source of Truth

Каждый Skill, Rule или Prompt существует в одном экземпляре.
Любые изменения производятся только в центральном репозитории контекста.

---

### Local First

Все данные находятся исключительно на локальном компьютере пользователя.
Приложение не требует облака.

---

### File Based

Источником данных является файловая система.
Использование базы данных в MVP не допускается.

---

### Human Readable

Все данные должны храниться в обычных Markdown-файлах с YAML Frontmatter.
Файлы должны оставаться пригодными для ручного редактирования.

---

### IDE Agnostic

Внутреннее представление контекстных объектов не должно зависеть от конкретной IDE.
Поддержка новой IDE должна сводиться к реализации нового Connector без изменения существующей модели данных.

---

### Explicit Export

Экспорт выполняется только по явному действию пользователя.
Автоматическая двусторонняя синхронизация не реализуется.

---

### Minimal Abstraction

Не создавать сложную доменную модель.
Не строить полноценный Knowledge Graph.
Не использовать ORM, базы данных или сложные DSL.
Проект должен оставаться простым и понятным.

---

## 1.5 Область применения

Приложение ориентировано на разработчиков программного обеспечения, активно использующих AI при разработке.

Типичные сценарии:
- использование нескольких IDE одновременно;
- переключение между рабочими и личными проектами;
- поддержка собственной библиотеки Skills;
- ведение корпоративных правил;
- хранение коллекции Prompt'ов;
- работа с локальными AI-моделями.
    

---

## 1.6 Основные сценарии использования

### Сценарий 1

Разработчик создает новый Skill.

После сохранения экспортирует его сразу:
- в Zed;
- в Kilo Code;
- в Explyt.
    

---

### Сценарий 2

Разработчик изменяет существующее Rule.
Экспортирует только в Explyt.

---

### Сценарий 3

Разработчик открывает библиотеку Prompt'ов.
Находит нужный Prompt.
Копирует его в буфер обмена.
Использует в любом AI-чате.

---

### Сценарий 4

Разработчик подключает Zed к встроенному MCP Server.
Prompt автоматически появляется в списке Slash-команд Zed.

---

## 1.7 Ограничения MVP

Первая версия приложения сознательно ограничивается следующими возможностями.

Поддерживаются только:
- локальная файловая система;
- Markdown;
- YAML Frontmatter;
- экспорт контекстных объектов;
- встроенный MCP Server для Prompt'ов.
    

Не реализуются:
- совместная работа;
- авторизация;
- облачная синхронизация;
- Git-интеграция;
- поиск по содержимому;
- история изменений;
- версионирование;
- двусторонний импорт изменений;
- поддержка бинарных файлов.
    

---

## 1.8 Терминология

### Context Item

Любой контекстный объект, используемый AI: Skill, Rule или Prompt.

---

### Skill

Большая специализированная инструкция, описывающая экспертные материалы, архитектуру, процесс разработки или конкретную предметную область.

---

### Rule

Набор ограничений или правил поведения AI.
Как правило, применяется автоматически во время работы агента.

---

### Prompt

Шаблон пользовательского запроса.
Используется вручную либо публикуется через MCP.
Prompt не экспортируется в файловую структуру IDE.

---

### Connector

Компонент, отвечающий за экспорт контекстных объектов в конкретную IDE или AI-плагин.

Каждая IDE реализуется собственным Connector.

---

### Export

Процесс преобразования внутреннего представления контекстных объектов в формат конкретной IDE с последующей записью в файловую систему.
Экспорт всегда односторонний.

---

### MCP Server

Встроенный сервер FastMCP, публикующий Prompt'ы через протокол Model Context Protocol.

---

# Часть 2. Общая архитектура

## 2.1 Архитектурный обзор

Архитектура приложения строится вокруг единого локального репозитория контекста.

Все операции производятся относительно него.

Никакая IDE не рассматривается как источник данных.

Все IDE являются исключительно получателями экспортируемых контекстных объектов.

Таким образом приложение реализует модель **Single Source of Truth**, в которой любое изменение сначала попадает в центральное хранилище, а затем при необходимости экспортируется в одну или несколько целевых сред.

---

## 2.2 Высокоуровневая архитектура

```text
                 +------------------------+
                 |      Web UI (Reflex)   |
                 +-----------+------------+
                             |
                             |
                 +-----------v------------+
                 |        App State       |
                 +-----------+------------+
                             |
        +--------------------+--------------------+
        |                    |                    |
        |                    |                    |
+-------v-------+   +--------v--------+   +------v-------+
| File Manager  |   | Export Engine   |   | MCP Server   |
+-------+-------+   +--------+--------+   +------+-------+
        |                    |                   |
        |                    |                   |
        |         +----------+----------+        |
        |         |                     |        |
        |         |                     |        |
        |   +-----v-----+        +------v-----+  |
        |   | Connector |        | Connector  |  |
        |   |   Zed     |        | Kilo Code  |  |
        |   +-----------+        +------------+  |
        |                                        |
        |                              +---------v---------+
        |                              |     Explyt        |
        |                              +-------------------+
        |
+-------v----------------------------------------+
|          Local Context Repository              |
+------------------------------------------------+
```

---

## 2.3 Основные подсистемы

Архитектура приложения состоит из пяти независимых подсистем.

### Context Repository

Центральное файловое хранилище AI-контекста.

Содержит:
- Skills;
- Rules;
- Prompts.
    

Является единственным местом хранения пользовательских данных.

---

### File Manager

Отвечает за работу с файловой системой.

Основные задачи:
- чтение файлов;
- запись;
- создание;
- удаление;
- построение дерева каталогов;
- парсинг YAML Frontmatter.
    

File Manager ничего не знает о конкретных IDE.

---

### Export Engine

Центральный координатор процесса экспорта.

Отвечает за:
- выбор Connector;
- подготовку объектов;
- запуск экспорта;
- обработку ошибок;
- ведение журнала операций.
    

Export Engine не содержит логики конкретных IDE.

Вся специфическая логика находится внутри Connector'ов.

---

### Connectors

Каждая поддерживаемая IDE реализуется отдельным Connector.

Connector отвечает за:
- экспорт Skills;
- экспорт Rules;
- особенности структуры каталогов;
- особенности metadata;
- проверку совместимости;
- удаление экспортированных файлов;
- получение статуса экспорта.
    

Connector ничего не знает о пользовательском интерфейсе.

---

### MCP Server

Встроенный FastMCP Server.

Является частью приложения.

Не требует отдельного процесса.

Используется исключительно для публикации Prompt'ов.

При отключении MCP остальная функциональность приложения продолжает работать без изменений.

---

## 2.4 Потоки данных

В системе существуют два независимых потока данных.

### Поток экспорта

```text
Context Repository
        ↓
Export Engine
        ↓
Connector
        ↓
IDE
```

Используется для Skills и Rules.

---

### Поток публикации Prompt'ов

```text
Context Repository
        ↓
Prompt Manager
        ↓
 ┌───────────────┬────────────────┐
 │               │                │
 ▼               ▼                ▼
Copy        Prompt Gallery    MCP Server
```

Prompt'ы не участвуют в механизме экспорта.

Они используются либо напрямую через пользовательский интерфейс, либо публикуются через встроенный MCP Server.

---

## 2.5 Архитектурные принципы

При реализации приложения необходимо придерживаться следующих правил.

### Разделение ответственности

Каждая подсистема должна выполнять только одну задачу.

Например:
- File Manager не экспортирует файлы;
- Connector не занимается UI;
- MCP Server не знает о файловой синхронизации.
    

---

### Независимость компонентов

Подсистемы должны взаимодействовать только через четко определенные интерфейсы.

Это позволит в дальнейшем:
- добавлять новые Connector'ы;
- изменять внутреннюю реализацию Export Engine;
- расширять поддержку IDE без изменения существующего кода.
    

---

### Простота реализации

Несмотря на модульную архитектуру, приложение остается относительно небольшим.

Не используются:
- Dependency Injection контейнеры;
- Event Bus;
- CQRS;
- сложные шаблоны проектирования;
- микросервисная архитектура.
    

Каждая подсистема представляет собой обычный Python-модуль с минимальным количеством зависимостей.

# Часть 3. Модель данных

## 3.1 Общие положения

В MVP используются три независимых типа данных:

- **Skill** — специализированная инструкция или набор контекстных материалов;
- **Rule** — правило поведения AI-агента;
- **Prompt** — готовый пользовательский запрос.

Тип объекта определяется его расположением в репозитории:

```text
skills/   → Skill
rules/    → Rule
prompts/  → Prompt
```

Дополнительное поле `kind` во frontmatter не требуется.

Все объекты хранятся в текстовом формате:

- кодировка UTF-8;
- Markdown для содержимого;
- YAML Frontmatter для метаданных;
- переносы строк при записи нормализуются в `LF`;
- база данных не используется.

Skills и Rules участвуют в экспорте через Connector'ы. Prompts не экспортируются в файловые структуры IDE и доступны через UI и MCP.

---

## 3.2 Общий формат Markdown-файла

Каждый файл состоит из двух частей:

1. YAML Frontmatter;
2. Markdown body.

Пример:

```markdown
---
title: Python Code Review
description: Review Python code according to project standards
tags:
  - python
  - review
version: "1.0"
status: active
---

# Python Code Review

Review the supplied Python code.

Pay particular attention to:

- correctness;
- typing;
- error handling;
- testability.
```

Frontmatter должен располагаться в начале файла и быть ограничен строками `---`.

```text
---
<valid YAML>
---
<markdown body>
```

Пустой frontmatter допускается технически, но такой объект считается невалидным, если для его типа отсутствуют обязательные поля.

---

## 3.3 Общие метаданные

Для Skill, Rule и Prompt используется небольшой общий набор полей.

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `title` | `string` | Да | Человекочитаемое название |
| `description` | `string` | Да | Краткое описание объекта |
| `tags` | `list[string]` | Нет | Теги для фильтрации и отображения |
| `aliases` | `list[string]` | Нет | Альтернативные названия |
| `version` | `string` | Нет | Пользовательская версия объекта |
| `authors` | `list[string]` | Нет | Авторы или владельцы содержимого |
| `status` | `string` | Нет | Статус объекта |
| `enabled` | `boolean` | Нет | Доступен ли объект для экспорта или публикации |

Допустимые значения `status` в MVP:

- `draft`;
- `active`;
- `deprecated`;
- `archived`.

Если поле `status` отсутствует, используется значение `active`.

Если поле `enabled` отсутствует, используется значение `true`.

Пример полного общего frontmatter:

```yaml
---
title: Python Code Review
description: Rules and recommendations for reviewing Python code
tags:
  - python
  - review
aliases:
  - python-review
version: "1.2"
authors:
  - Sasha
status: active
enabled: true
---
```

Поля, неизвестные текущей версии приложения, не должны удаляться при редактировании и сохранении файла. Connector может игнорировать поля, которые не поддерживаются целевой IDE.

---

## 3.4 Идентификаторы объектов

Отдельное обязательное поле `id` в MVP не вводится.

Идентификатор определяется из относительного пути объекта.

### Для Skill

Идентификатором является относительный путь каталога Skill внутри `skills/`.

```text
skills/python-review/SKILL.md
```

Идентификатор:

```text
python-review
```

Для вложенной структуры:

```text
skills/python/review/SKILL.md
```

Идентификатор:

```text
python/review
```

### Для Rule

Идентификатором является относительный путь файла без расширения:

```text
rules/python/strict-typing.md
```

Идентификатор:

```text
python/strict-typing
```

### Для Prompt

Идентификатором является относительный путь файла без расширения:

```text
prompts/review/code-review.md
```

Внутренний идентификатор:

```text
review/code-review
```

Для MCP из него формируется безопасное имя. Разделители каталогов заменяются на `-`:

```text
review-code-review
```

Имена MCP Prompt должны быть уникальны после такой нормализации. Конфликты должны обнаруживаться при загрузке Prompt Library и отображаться как ошибка валидации.

---

## 3.5 Модель Skill

### 3.5.1 Назначение

Skill содержит специализированные материалы или инструкции, которые могут быть экспортированы в нативный формат Skill конкретной IDE.

Примеры:

- правила проведения code review;
- рекомендации по работе с конкретным фреймворком;
- архитектурные соглашения;
- инструкции по диагностике ошибок;
- описание рабочего процесса команды.

---

### 3.5.2 Физический формат

Skill хранится как каталог, содержащий обязательный файл `SKILL.md`.

```text
skills/
└── python-review/
    └── SKILL.md
```

Каталожная структура выбрана потому, что поддерживаемые IDE используют или допускают представление Skill как отдельного каталога с основным файлом `SKILL.md`.

В MVP Skill содержит только Markdown-файлы. Скрипты, изображения, бинарные вложения и исполняемые ресурсы не поддерживаются.

---

### 3.5.3 Поля Skill

Skill использует общие метаданные и может содержать следующие дополнительные поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `name` | `string` | Нет | Машиночитаемое имя для экспорта |
| `compatibility` | `list[string]` | Нет | Ограничение списка целевых Connector'ов |
| `dependencies` | `list[string]` | Нет | Информационный список зависимостей |
| `activation` | `string` | Нет | Информация о предполагаемом режиме активации |

Допустимые значения `activation` в MVP:

- `automatic`;
- `manual`;
- `both`.

Это поле является внутренней метаинформацией. Connector экспортирует его только в том случае, если целевой формат поддерживает соответствующее понятие.

Если `name` отсутствует, используется имя каталога Skill.

Пример:

```markdown
---
name: python-review
title: Python Code Review
description: Review Python code for correctness and maintainability
tags:
  - python
  - review
version: "1.0"
status: active
enabled: true
compatibility:
  - zed
  - kilo_code
  - explyt
activation: both
dependencies: []
---

# Python Code Review

Use this skill when reviewing Python code.

## Checklist

- Check typing.
- Check exception handling.
- Check public API consistency.
- Check test coverage.
```

---

### 3.5.4 Совместимость Skill

Поле `compatibility` является необязательным.

Если оно отсутствует, Skill считается доступным для всех включённых Connector'ов, поддерживающих Skills.

Если оно указано, экспорт разрешён только в перечисленные Connector'ы.

Например:

```yaml
compatibility:
  - zed
  - kilo_code
```

Такой Skill не должен экспортироваться через Connector Explyt.

Connector также может пропустить Skill, если не способен корректно представить его обязательные данные. Причина пропуска должна попадать в журнал экспорта.

---

### 3.5.5 Дополнительные Markdown-файлы Skill

MVP допускает дополнительные Markdown-файлы внутри каталога Skill:

```text
skills/python-review/
├── SKILL.md
├── checklist.md
└── examples.md
```

Connector самостоятельно определяет, поддерживает ли целевая IDE такие файлы.

В базовом варианте:

- `SKILL.md` экспортируется всегда;
- дополнительные `.md`-файлы копируются с сохранением относительной структуры, если Connector это поддерживает;
- если Connector не поддерживает дополнительные файлы, они пропускаются с предупреждением;
- ссылки между Markdown-файлами не переписываются автоматически.

---

## 3.6 Модель Rule

### 3.6.1 Назначение

Rule задаёт постоянное правило поведения AI-агента.

Примеры:

- всегда использовать `pytest`;
- не использовать определённую библиотеку;
- соблюдать правила именования;
- отвечать на определённом языке;
- следовать архитектурным ограничениям проекта.

Rule может быть экспортирован:

- как отдельный файл;
- как часть агрегированного файла правил;
- как IDE-specific instruction.

Конкретный способ определяется Connector'ом.

---

### 3.6.2 Физический формат

Rule хранится как отдельный Markdown-файл:

```text
rules/
├── use-pytest.md
├── strict-typing.md
└── architecture/
    └── dependency-direction.md
```

---

### 3.6.3 Поля Rule

Rule использует общие метаданные и может содержать дополнительные поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `priority` | `integer` | Нет | Порядок применения или агрегации |
| `scope` | `string` | Нет | Предполагаемая область применения |
| `compatibility` | `list[string]` | Нет | Список разрешённых Connector'ов |

Допустимые значения `scope`:

- `global`;
- `project`.

Значение по умолчанию:

```text
project
```

`scope` описывает намерение пользователя, но не заменяет выбор проекта в настройках Connector. Фактический каталог назначения определяется конфигурацией экспорта.

`priority` используется при объединении нескольких Rule в один целевой файл. Меньшее значение означает более раннее расположение. Если `priority` отсутствует, используется значение `100`.

Пример:

```markdown
---
title: Use pytest
description: Require pytest for all Python tests
tags:
  - python
  - testing
priority: 20
scope: project
status: active
enabled: true
compatibility:
  - kilo_code
  - explyt
---

# Testing framework

Always use `pytest` for Python tests.

Do not introduce new tests based on `unittest.TestCase`.
```

---

### 3.6.4 Порядок Rule

Если Connector объединяет несколько Rule в один файл, порядок определяется следующим образом:

1. `priority` по возрастанию;
2. относительный путь файла в лексикографическом порядке.

Таким образом экспорт должен быть детерминированным и давать одинаковый результат при неизменном source repository.

---

## 3.7 Модель Prompt

### 3.7.1 Назначение

Prompt является готовым пользовательским запросом.

Prompt:

- отображается в Prompt Gallery;
- может копироваться в буфер обмена;
- может публиковаться через MCP;
- не передаётся в Export Engine;
- не экспортируется Connector'ами в файловые каталоги IDE.

---

### 3.7.2 Физический формат

Prompt хранится как отдельный Markdown-файл:

```text
prompts/
├── review-code.md
├── generate-tests.md
└── architecture/
    └── explain-decision.md
```

---

### 3.7.3 Поля Prompt

Prompt использует общие метаданные и содержит следующие дополнительные поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `mcp_enabled` | `boolean` | Нет | Публиковать ли Prompt через MCP |
| `mcp_name` | `string` | Нет | Явное имя Prompt в MCP |
| `copy_mode` | `string` | Нет | Какая часть файла копируется в буфер |

Допустимые значения `copy_mode`:

- `body` — копировать только Markdown body;
- `full` — копировать весь файл вместе с frontmatter.

Значение по умолчанию:

```text
body
```

Если `mcp_enabled` отсутствует, используется значение `true`.

Если `mcp_name` отсутствует, оно формируется из относительного пути Prompt.

Пример:

```markdown
---
title: Review Code
description: Review the supplied code and identify important problems
tags:
  - review
  - quality
status: active
enabled: true
mcp_enabled: true
mcp_name: review_code
copy_mode: body
---

Review the supplied code.

Focus on:

1. correctness;
2. security;
3. maintainability;
4. missing tests.

Return findings in descending order of severity.
```

---

### 3.7.4 Правила публикации Prompt через MCP

Prompt публикуется через MCP только при одновременном выполнении условий:

- глобальная настройка MCP `enabled: true`;
- объект имеет `enabled: true`;
- объект имеет `mcp_enabled: true`;
- `status` равен `active`;
- frontmatter успешно прошёл валидацию;
- MCP-имя Prompt уникально.

В MVP поддерживаются статические Prompt без параметров и шаблонных переменных.

Аргументы MCP Prompt, формы заполнения переменных и Jinja-шаблонизация Prompt не входят в MVP.

---

### 3.7.5 Правила копирования Prompt

При нажатии кнопки **Copy**:

1. приложение читает актуальный файл с диска;
2. определяет `copy_mode`;
3. при `body` удаляет YAML Frontmatter;
4. при `full` использует исходное содержимое файла;
5. передаёт результат в `rx.set_clipboard`;
6. показывает уведомление об успешном копировании.

Отключённые и черновые Prompt могут отображаться в UI редактора, но не должны отображаться в основной галерее по умолчанию.

---

## 3.8 Парсинг YAML Frontmatter

Парсинг выполняется File Manager с помощью `yaml.safe_load`.

Алгоритм:

1. прочитать файл как UTF-8;
2. проверить, начинается ли файл со строки `---`;
3. найти следующую отдельную строку `---`;
4. передать содержимое между разделителями в `yaml.safe_load`;
5. проверить, что результат является словарём;
6. сохранить оставшийся текст как Markdown body.

Если frontmatter отсутствует или невалиден:

- файл остаётся доступным для редактирования;
- объект помечается как невалидный;
- экспорт или MCP-публикация объекта блокируется;
- ошибка показывается в UI и журнале операций;
- остальные валидные объекты продолжают обрабатываться.

---

## 3.9 Валидация

### Общие проверки

Для всех типов выполняются следующие проверки:

- файл находится внутри `source_dir`;
- расширение файла соответствует ожидаемому;
- файл читается как UTF-8;
- frontmatter является YAML mapping;
- `title` является непустой строкой;
- `description` является непустой строкой;
- `tags`, `aliases`, `authors` являются списками строк;
- `enabled` является boolean;
- `status` содержит поддерживаемое значение.

### Проверки Skill

- основной файл называется `SKILL.md`;
- имя каталога не пустое;
- `name`, если задано, является строкой;
- `compatibility` является списком строк;
- `activation` содержит допустимое значение.

### Проверки Rule

- файл имеет расширение `.md`;
- `priority` является целым числом;
- `scope` содержит допустимое значение;
- `compatibility` является списком строк.

### Проверки Prompt

- файл имеет расширение `.md`;
- `mcp_enabled` является boolean;
- `mcp_name` является строкой и допустимым MCP-именем;
- `copy_mode` содержит допустимое значение;
- итоговое MCP-имя уникально.

---

## 3.10 Состояния объектов

В UI объект может иметь одно из вычисляемых состояний:

| Состояние | Значение |
|---|---|
| `valid` | Объект корректен и доступен для использования |
| `draft` | Объект сохранён, но не публикуется по умолчанию |
| `disabled` | Объект отключён через `enabled: false` |
| `deprecated` | Объект устарел, но оставлен в репозитории |
| `archived` | Объект исключён из обычных операций |
| `invalid` | Ошибка структуры или metadata |

Экспортируются только объекты, которые:

- валидны;
- имеют `enabled: true`;
- имеют `status: active`;
- совместимы с выбранным Connector.

---

## 3.11 Сохранение исходных данных

При экспорте исходный файл никогда не изменяется.

Connector получает:

- относительный путь;
- тип объекта;
- frontmatter;
- Markdown body;
- исходный текст;
- дополнительные Markdown-файлы Skill, если они существуют.

Connector формирует отдельное целевое представление.

IDE-specific metadata не должна записываться обратно в source-файл автоматически.

# Часть 4. Структура каталогов и файлов

## 4.1 Общая структура

Система использует два независимых набора каталогов:

1. каталог самого приложения;
2. пользовательский Context Repository.

Пример:

```text
~/projects/context-desk/            ← исходный код приложения
~/context-desk/                     ← пользовательские данные
```

Context Repository не обязан находиться внутри проекта приложения.

Путь задаётся через `source_dir` в `settings.yaml`.

---

## 4.2 Структура Context Repository

Рекомендуемая структура:

```text
~/context-desk/
├── skills/
│   ├── python-review/
│   │   ├── SKILL.md
│   │   ├── checklist.md
│   │   └── examples.md
│   └── dotnet-ef-core/
│       └── SKILL.md
│
├── rules/
│   ├── common/
│   │   └── concise-responses.md
│   ├── python/
│   │   ├── use-pytest.md
│   │   └── strict-typing.md
│   └── dotnet/
│       └── nullable-enabled.md
│
└── prompts/
    ├── review-code.md
    ├── generate-tests.md
    └── architecture/
        └── explain-decision.md
```

Обязательные корневые каталоги:

```text
skills/
rules/
prompts/
```

Если какой-либо каталог отсутствует, приложение должно создать его при инициализации Context Repository либо по явному подтверждению пользователя.

---

## 4.3 Каталог Skills

Каждый Skill размещается в отдельном каталоге:

```text
skills/<skill-path>/SKILL.md
```

Примеры:

```text
skills/python-review/SKILL.md
skills/testing/pytest/SKILL.md
skills/dotnet/entity-framework/SKILL.md
```

Внутри Skill допускаются дополнительные Markdown-файлы:

```text
skills/dotnet/entity-framework/
├── SKILL.md
├── conventions.md
├── examples.md
└── troubleshooting.md
```

Правила:

- `SKILL.md` обязателен;
- регистр имени `SKILL.md` фиксирован;
- каталог без `SKILL.md` не считается Skill;
- дополнительные подкаталоги допускаются;
- в MVP обрабатываются только `.md`-файлы;
- символьные ссылки не обходятся;
- скрытые файлы и каталоги игнорируются.

---

## 4.4 Каталог Rules

Rules хранятся в виде отдельных Markdown-файлов:

```text
rules/**/*.md
```

Допускается тематическая группировка:

```text
rules/
├── global/
├── languages/
│   ├── python/
│   └── csharp/
├── architecture/
└── testing/
```

Структура каталогов является организационной и сохраняется при экспорте только в том случае, если это поддерживает Connector.

Если целевая IDE использует один агрегированный файл правил, Connector объединяет все подходящие Rule независимо от их исходной структуры.

---

## 4.5 Каталог Prompts

Prompts хранятся как отдельные Markdown-файлы:

```text
prompts/**/*.md
```

Пример:

```text
prompts/
├── code/
│   ├── review.md
│   └── explain.md
├── tests/
│   ├── generate.md
│   └── diagnose-failure.md
└── writing/
    └── improve-documentation.md
```

Структура каталогов используется:

- для группировки в UI;
- для формирования внутреннего идентификатора;
- для формирования MCP-имени, если `mcp_name` не задан явно.

Prompts не копируются в целевые каталоги Connector'ов.

## 4.8 Простые внутренние модели Python

Внутренние модели не должны превращаться в отдельную сложную доменную систему.

Достаточно использовать `dataclass` или аналогичные простые структуры.

Пример:

```python
from dataclasses import dataclass, field
from pathlib import Path
from typing import Any


@dataclass
class ContextItem:
    relative_path: Path
    source_path: Path
    metadata: dict[str, Any]
    body: str
    raw_content: str
    errors: list[str] = field(default_factory=list)

    @property
    def is_valid(self) -> bool:
        return not self.errors


@dataclass
class SkillItem(ContextItem):
    skill_dir: Path | None = None
    additional_files: list[Path] = field(default_factory=list)


@dataclass
class RuleItem(ContextItem):
    priority: int = 100


@dataclass
class PromptItem(ContextItem):
    mcp_name: str = ""
    mcp_enabled: bool = True
    copy_mode: str = "body"
```

Эти классы:

- не содержат бизнес-логику конкретных IDE;
- не записывают файлы самостоятельно;
- не зависят от Reflex;
- используются для передачи данных между File Manager, Export Engine, Connector'ами и MCP Server.

---

## 4.9 Каталог шаблонов

Jinja2-шаблоны хранятся отдельно от Connector-кода:

```text
templates/<connector>/<object-type>.md.j2
```

Примеры:

```text
templates/zed/skill.md.j2
templates/zed/rule.md.j2
templates/kilo_code/skill.md.j2
templates/kilo_code/rule.md.j2
templates/explyt/skill.md.j2
templates/explyt/rule.md.j2
```

Алгоритм выбора шаблона:

1. Connector ищет специализированный шаблон для типа объекта;
2. если он отсутствует, ищет `default.md.j2`;
3. если шаблон отсутствует полностью, используется Python-реализация Connector;
4. если Connector не способен экспортировать объект без шаблона, операция завершается ошибкой для этого объекта.

Шаблоны Prompts в MVP не используются.

---

## 4.10 Целевые каталоги

Целевые каталоги IDE не являются частью Context Repository.

Они задаются в `settings.yaml` отдельно для каждого Connector и проекта.

Пример:

```text
Context Repository
~/context-desk/

Target Zed
~/.config/zed/...
~/projects/project-x/.zed/...

Target Kilo Code
~/projects/project-x/.kilocode/...

Target Explyt
~/projects/project-x/.explyt/...
```

Точная структура внутри target определяется Connector'ом, а не общим Export Engine.

`target_dir` означает корневой каталог интеграции. Connector самостоятельно добавляет необходимые подкаталоги, например `skills/` или `rules/`.

---

## 4.11 Управляемые экспортом файлы

Приложение не должно удалять произвольные пользовательские файлы из target-каталога.

Для безопасного удаления необходимо вести manifest экспортированных файлов.

Рекомендуемая структура:

```text
<target_dir>/
└── .context-desk/
    └── manifest.json
```

Manifest содержит:

- имя Connector;
- ключ проекта;
- время последнего экспорта;
- список созданных приложением файлов;
- идентификаторы исходных объектов;
- контрольные суммы экспортированного содержимого.

Пример:

```json
{
  "connector": "kilo_code",
  "project": "project-x",
  "exported_at": "2026-08-07T14:30:00Z",
  "files": [
    {
      "source_id": "python-review",
      "source_type": "skill",
      "target_path": "skills/python-review/SKILL.md",
      "sha256": "..."
    }
  ]
}
```

Операция **Delete Exported** удаляет только файлы, перечисленные в manifest.

Если manifest отсутствует, массовое удаление target-каталога запрещается.

---

## 4.12 Временные файлы и атомарная запись

Запись source- и target-файлов должна выполняться атомарно:

1. сформировать содержимое;
2. записать его во временный файл в том же каталоге;
3. при необходимости выполнить flush;
4. заменить целевой файл через `Path.replace()`.

Пример временного имени:

```text
SKILL.md.context-desk.tmp
```

После успешной операции временный файл должен быть удалён или заменён.

При ошибке существующий целевой файл должен остаться неизменным.

---

## 4.13 Работа с путями

Для всех операций используется `pathlib.Path`.

Обязательные правила:

- `~` раскрывается через `Path.expanduser()`;
- относительные пути разрешаются относительно явно определённой базы;
- перед записью проверяется, что итоговый путь находится внутри разрешённого каталога;
- конструкции `..` не должны позволять выйти за пределы `source_dir` или `target_dir`;
- пользовательский ввод не конкатенируется с путями строковыми операциями;
- символьные ссылки при рекурсивном сканировании не обходятся;
- абсолютные пути внутри Context Repository не сохраняются в metadata.

---

## 4.14 Игнорируемые файлы

При сканировании игнорируются:

- скрытые каталоги, начинающиеся с `.`;
- временные файлы редакторов;
- файлы, заканчивающиеся на `~`;
- `*.tmp`;
- `*.swp`;
- `*.bak`;
- `__pycache__/`;
- системные файлы наподобие `.DS_Store`;
- manifest и внутренние служебные каталоги приложения.

Дополнительные ignore-паттерны могут быть добавлены в конфигурацию в следующих версиях.

---

## 4.15 Инициализация нового репозитория

Если `source_dir` существует, но не содержит ожидаемой структуры, приложение должно предложить инициализацию.

Инициализация создаёт:

```text
<source_dir>/
├── skills/
├── rules/
└── prompts/
```

Приложение не должно удалять или перезаписывать существующие пользовательские файлы.

Если `source_dir` не существует, его создание допускается только после явного действия пользователя или при первом запуске с подтверждением.

---

## 4.16 Ограничения файловой структуры MVP

В MVP не поддерживаются:

- бинарные вложения;
- изображения Skill;
- исполняемые скрипты внутри Skill;
- символические ссылки;
- файлы за пределами `source_dir`;
- несколько основных файлов одного Skill;
- отдельные metadata-файлы;
- автоматическое переписывание внутренних Markdown-ссылок;
- импорт файлов из target обратно в Context Repository;
- наблюдение за каталогами в реальном времени.

Обновление данных выполняется при:

- открытии страницы;
- сохранении файла;
- создании или удалении объекта;
- нажатии кнопки **Refresh**;
- запуске экспорта;
- обработке MCP-запроса, если включено перечитывание Prompt с диска.

---

# Часть 5. Конфигурация приложения

## 5.1 Общие положения

Основная пользовательская конфигурация хранится в файле:

```text
settings.yaml
```

Конфигурация определяет:

- расположение Context Repository;
- параметры встроенного MCP Server;
- включённые Connector'ы;
- поддерживаемые способы доставки AI-контекста;
- проекты и целевые каталоги;
- опции экспорта;
- параметры UI и журналирования.

`settings.yaml` является единственным конфигурационным файлом MVP. Переменные окружения могут использоваться только для переопределения отдельных системных параметров запуска.

Конфигурация:

- читается при старте приложения;
- может быть перечитана через UI;
- валидируется до применения;
- сохраняется атомарно;
- не должна содержать секреты.

---

## 5.2 Полный пример `settings.yaml`

```yaml
version: 1

source_dir: "~/context-desk"

application:
  language: ru
  theme: dark
  open_browser: true
  log_level: info
  max_log_entries: 500

mcp:
  enabled: true
  transport: streamable_http
  host: "127.0.0.1"
  port: 8080
  path: "/mcp"
  server_name: "Context Desk"
  refresh_on_request: true

connectors:
  zed:
    enabled: true
    label: "Zed"
    supports:
      skills: true
      rules: true
      prompts: mcp

    projects:
      global:
        label: "Global"
        target_dir: "~/.config/zed"

      project_x:
        label: "Project X"
        target_dir: "~/projects/project-x"

    options:
      skill_export_mode: native
      rule_export_mode: instructions
      overwrite: managed_only

  kilo_code:
    enabled: true
    label: "Kilo Code"

    supports:
      skills: true
      rules: true
      prompts: false

    projects:
      project_x:
        label: "Project X"
        target_dir: "~/projects/project-x"

    options:
      skill_export_mode: native
      rule_export_mode: separate
      overwrite: managed_only

  explyt:
    enabled: true
    label: "Explyt"

    supports:
      skills: true
      rules: true
      prompts: false

    projects:
      project_x:
        label: "Project X"
        target_dir: "~/projects/project-x"

    options:
      skill_export_mode: native
      rule_export_mode: separate
      overwrite: managed_only
```

Точные подкаталоги внутри `target_dir` определяются реализацией соответствующего Connector.

Например, `target_dir` может указывать на корень проекта, а Connector самостоятельно сформирует путь к каталогу Skills или Rules.

---

## 5.3 Версия формата конфигурации

Поле `version` обязательно.

```yaml
version: 1
```

Оно используется для будущей миграции структуры `settings.yaml`.

В MVP поддерживается только:

```text
version = 1
```

Если версия отсутствует или не поддерживается:

- приложение не запускает экспорт;
- MCP Server не запускается;
- UI открывается в режиме ошибки конфигурации;
- пользователю показывается понятное сообщение;
- исходный файл не изменяется автоматически.

Автоматическая миграция между версиями не входит в MVP.

---

## 5.4 Путь к Context Repository

```yaml
source_dir: "~/context-desk"
```

Поле `source_dir` обязательно.

Требования:

- значение должно быть строкой;
- поддерживается `~`;
- путь может быть абсолютным или относительным;
- относительный путь разрешается относительно каталога `settings.yaml`;
- после разрешения путь должен указывать на каталог;
- приложение должно проверять права чтения и записи.

Если каталог не существует, приложение предлагает создать его и инициализировать стандартную структуру:

```text
skills/
rules/
prompts/
```

Изменение `source_dir` через UI не перемещает существующие файлы. Оно только переключает приложение на другой Context Repository.

---

## 5.5 Секция `application`

Секция содержит общие настройки приложения.

```yaml
application:
  language: ru
  theme: dark
  open_browser: true
  log_level: info
  max_log_entries: 500
```

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `language` | `string` | `ru` | Язык пользовательского интерфейса |
| `theme` | `string` | `dark` | Тема интерфейса |
| `open_browser` | `boolean` | `true` | Открывать браузер при локальном запуске |
| `log_level` | `string` | `info` | Уровень журналирования |
| `max_log_entries` | `integer` | `500` | Максимальное число записей в UI-журнале |

Допустимые значения `theme`:

- `dark`;
- `light`;
- `system`.

Допустимые значения `log_level`:

- `debug`;
- `info`;
- `warning`;
- `error`.

Локализация интерфейса за пределами русского и английского языков не является обязательной для MVP.

---

## 5.6 Секция `mcp`

Секция настраивает встроенный MCP Server.

```yaml
mcp:
  enabled: true
  transport: streamable_http
  host: "127.0.0.1"
  port: 8080
  path: "/mcp"
  server_name: "Context Desk"
  refresh_on_request: true
```

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `enabled` | `boolean` | `false` | Запускать ли MCP Server |
| `transport` | `string` | `streamable_http` | MCP transport |
| `host` | `string` | `127.0.0.1` | Интерфейс прослушивания |
| `port` | `integer` | `8080` | TCP-порт сервера |
| `path` | `string` | `/mcp` | HTTP endpoint MCP |
| `server_name` | `string` | `Context Desk` | Имя сервера для MCP-клиента |
| `refresh_on_request` | `boolean` | `true` | Перечитывать Prompt'ы при запросах |

В MVP обязательным transport является:

```text
streamable_http
```

SSE и `stdio` могут быть добавлены позднее, но не являются обязательными для первой версии.

---

## 5.7 Ограничения безопасности MCP

По умолчанию MCP Server должен слушать только loopback-интерфейс:

```yaml
host: "127.0.0.1"
```

Допустим также IPv6 loopback:

```yaml
host: "::1"
```

Использование внешнего интерфейса, например:

```yaml
host: "0.0.0.0"
```

должно приводить как минимум к заметному предупреждению в UI и журнале.

Причина: Prompt'ы могут содержать:

- внутренние инструкции;
- корпоративные правила;
- фрагменты проектного контекста;
- другую информацию, не предназначенную для публикации в локальной сети.

Авторизация MCP Server в MVP не реализуется. Поэтому рекомендуемый и безопасный режим работы — только `localhost`.

---

## 5.8 Обновление Prompt Library для MCP

Поле:

```yaml
refresh_on_request: true
```

определяет способ загрузки Prompt'ов.

### При значении `true`

Перед обработкой `prompts/list` и `prompts/get` Prompt Manager проверяет актуальное состояние файлов.

Преимущества:

- изменения сразу становятся доступны MCP-клиенту;
- не требуется перезапуск сервера.

Недостаток:

- дополнительное чтение файловой системы.

### При значении `false`

MCP Server использует кэш Prompt Library.

Кэш обновляется:

- при запуске;
- после сохранения Prompt через UI;
- после создания или удаления Prompt;
- при нажатии **Refresh**;
- после перезагрузки конфигурации.

Для локального MVP рекомендуется:

```yaml
refresh_on_request: true
```

---

## 5.9 Секция `connectors`

Каждый Connector описывается отдельным элементом:

```yaml
connectors:
  <connector_name>:
    enabled: true
    label: "..."
    supports: {}
    projects: {}
    options: {}
```

Ключ Connector должен совпадать с именем зарегистрированной реализации:

```text
zed
kilo_code
explyt
```

Неизвестный Connector:

- не должен приводить к падению всего приложения;
- отображается в UI как недоступный;
- не участвует в экспорте;
- создаёт предупреждение в журнале конфигурации.

---

## 5.10 Общие поля Connector

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `enabled` | `boolean` | Да | Включён ли Connector |
| `label` | `string` | Нет | Отображаемое имя |
| `supports` | `mapping` | Да | Настроенные способы доставки |
| `projects` | `mapping` | Да | Целевые проекты |
| `options` | `mapping` | Нет | Специфические настройки Connector |

Если `label` отсутствует, UI использует техническое имя Connector.

Отключённый Connector:

- отображается в Settings;
- не участвует в **Export All**;
- не запускает операции экспорта;
- не удаляет ранее экспортированные файлы автоматически.

Пользователь может вручную вызвать удаление ранее экспортированных файлов даже после отключения Connector, если доступен корректный manifest.

---

## 5.11 Секция `supports`

Пример:

```yaml
supports:
  skills: true
  rules: true
  prompts: mcp
```

Допустимые значения:

### Для `skills`

```yaml
skills: true
```

или:

```yaml
skills: false
```

### Для `rules`

```yaml
rules: true
```

или:

```yaml
rules: false
```

### Для `prompts`

```yaml
prompts: mcp
```

или:

```yaml
prompts: false
```

Значение `prompts: mcp` не означает, что Prompt экспортируется Connector'ом. Оно означает, что целевая среда может использовать Prompt Library через встроенный MCP Server.

Export Engine всегда игнорирует Prompts.

---

## 5.12 Фактические возможности Connector

Секция `supports` является декларативной конфигурацией, но не может расширить возможности реализации.

Например, если класс Connector объявляет:

```python
ConnectorCapabilities(
    skills=True,
    rules=False,
    mcp_prompts=False,
)
```

а в `settings.yaml` указано:

```yaml
supports:
  rules: true
```

конфигурация считается некорректной для этого Connector.

Применяется следующее правило:

```text
Фактическая возможность =
    возможность реализации Connector
    AND
    разрешение в settings.yaml
```

Таким образом пользователь может отключить поддерживаемый тип экспорта, но не может включить функциональность, которой нет в Connector.

---

## 5.13 Проекты Connector

Каждый Connector может содержать один или несколько проектов:

```yaml
projects:
  global:
    label: "Global"
    target_dir: "~/.config/zed"

  project_x:
    label: "Project X"
    target_dir: "~/projects/project-x"
```

Ключ проекта является стабильным техническим идентификатором.

### Поля проекта

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `label` | `string` | Нет | Название для UI |
| `target_dir` | `string` | Да | Корневой каталог назначения |
| `enabled` | `boolean` | Нет | Участвует ли проект в массовом экспорте |
| `options` | `mapping` | Нет | Переопределения опций Connector |

Пример:

```yaml
projects:
  project_x:
    label: "Project X"
    enabled: true
    target_dir: "~/projects/project-x"
    options:
      rule_export_mode: aggregate
```

Если `enabled` отсутствует, используется значение `true`.

---

## 5.14 Глобальные и проектные цели

Приложение не должно само определять, является ли target глобальным или проектным, только по пути.

Смысл проекта задаётся пользователем через идентификатор и label:

```yaml
global:
  label: "Global"
```

или:

```yaml
backend:
  label: "Backend Project"
```

Connector может учитывать специальные проектные параметры, но Export Engine рассматривает все проекты одинаково.

---

## 5.15 Наследование опций

Опции могут задаваться:

1. на уровне Connector;
2. на уровне конкретного проекта.

Пример:

```yaml
connectors:
  kilo_code:
    options:
      rule_export_mode: separate
      overwrite: managed_only

    projects:
      project_x:
        target_dir: "~/projects/project-x"
        options:
          rule_export_mode: aggregate
```

Итоговые опции `project_x`:

```yaml
rule_export_mode: aggregate
overwrite: managed_only
```

Проектные значения переопределяют значения Connector.

Вложенное глубокое объединение в MVP не требуется. Достаточно объединения верхнего уровня словаря `options`.

---

## 5.16 Общие опции экспорта

Connector может поддерживать следующие общие опции.

### `overwrite`

```yaml
overwrite: managed_only
```

Допустимые значения:

- `managed_only` — перезаписывать только файлы, известные по manifest;
- `always` — разрешать перезапись любого целевого файла;
- `never` — не перезаписывать существующие файлы.

Значение по умолчанию:

```text
managed_only
```

Режим `always` должен сопровождаться предупреждением в UI.

---

### `skill_export_mode`

```yaml
skill_export_mode: native
```

В MVP используется значение:

- `native` — экспорт в нативную структуру Skills целевой IDE.

Другие значения могут поддерживаться конкретным Connector, но не являются общими.

---

### `rule_export_mode`

```yaml
rule_export_mode: separate
```

Возможные значения:

- `separate` — отдельный целевой файл для каждого Rule;
- `aggregate` — объединение Rule в один файл;
- `instructions` — преобразование Rule в механизм Instructions целевой IDE.

Набор реально поддерживаемых значений определяется Connector.

---

## 5.17 Специфические опции Connector

Connector может определять дополнительные настройки:

```yaml
options:
  aggregate_file_name: "custom-rules.md"
  include_frontmatter: false
```

Требования:

- все специфические опции документируются в Connector;
- неизвестные опции вызывают предупреждение;
- неизвестная опция не должна молча изменять поведение;
- значения проходят валидацию до экспорта.

Для MVP не требуется универсальная схема внешних плагинов. Валидация может быть реализована обычным Python-кодом каждого встроенного Connector.

---

## 5.18 Переменные окружения

В MVP поддерживается минимальное переопределение настроек через переменные окружения:

| Переменная | Назначение |
|---|---|
| `AIKM_SETTINGS` | Путь к `settings.yaml` |
| `AIKM_SOURCE_DIR` | Переопределение `source_dir` |
| `AIKM_MCP_ENABLED` | Включение или отключение MCP |
| `AIKM_MCP_HOST` | Переопределение MCP host |
| `AIKM_MCP_PORT` | Переопределение MCP port |
| `AIKM_LOG_LEVEL` | Уровень журналирования |

Приоритет значений:

```text
значение по умолчанию
        ↓
settings.yaml
        ↓
переменная окружения
```

Переопределения окружения не записываются обратно в `settings.yaml`.

---

## 5.19 Валидация конфигурации

При загрузке проверяются:

- версия конфигурации;
- типы всех полей;
- существование зарегистрированных Connector'ов;
- уникальность ключей проектов;
- допустимость значений `supports`;
- соответствие `supports` возможностям реализации;
- допустимость Connector options;
- корректность MCP host, port и path;
- отсутствие конфликтов целевых путей;
- доступность `source_dir`.

Проверка прав записи в `target_dir` может выполняться непосредственно перед экспортом, поскольку каталог проекта может быть временно недоступен.

---

## 5.20 Ошибки конфигурации

Ошибки делятся на критические и некритические.

### Критические ошибки

- невалидный YAML;
- неподдерживаемая версия;
- отсутствующий `source_dir`;
- неправильный тип обязательного поля;
- некорректная секция `connectors`;
- недопустимый MCP port.

При критической ошибке:

- экспорт отключается;
- MCP Server не запускается;
- UI работает в ограниченном режиме;
- пользователю показывается список ошибок.

### Некритические ошибки

- неизвестный Connector;
- неизвестная опция;
- отключённый проект;
- временно недоступный target;
- конфликт декларативной возможности отдельного Connector.

Некритическая ошибка отключает только затронутую функцию или Connector.

---

## 5.21 Сохранение конфигурации

При сохранении через UI:

1. данные State валидируются;
2. формируется YAML;
3. содержимое записывается во временный файл;
4. исходный `settings.yaml` заменяется атомарно;
5. конфигурация перечитывается;
6. обновляется State;
7. при необходимости MCP Server перезапускается.

PyYAML не гарантирует сохранение комментариев и исходного форматирования. Поэтому в MVP допускается, что после сохранения через UI:

- порядок некоторых полей будет нормализован;
- стиль кавычек изменится;
- комментарии могут быть потеряны.

Это ограничение должно быть указано рядом с кнопкой сохранения настроек.

# Часть 6. Connector API

## 6.1 Назначение Connector

Connector инкапсулирует особенности конкретной IDE или AI-плагина.

Он отвечает за:

- проверку поддерживаемых типов контекстных объектов;
- выбор целевых относительных путей;
- преобразование Skills и Rules;
- формирование файлов для экспорта;
- проверку Connector-specific options;
- интерпретацию экспортного статуса.

Connector не отвечает за:

- чтение `settings.yaml`;
- управление Reflex State;
- показ уведомлений;
- запуск MCP Server;
- публикацию Prompt'ов;
- обход всего Context Repository;
- атомарную запись файлов;
- ведение общего журнала операций.

Эти задачи выполняют другие подсистемы.

---

## 6.2 Встроенные Connector'ы MVP

В MVP должны быть реализованы:

```text
ZedConnector
KiloCodeConnector
ExplytConnector
```

Расположение:

```text
context_desk/connectors/
├── __init__.py
├── base.py
├── zed.py
├── kilo_code.py
└── explyt.py
```

Динамическая загрузка сторонних Connector'ов через Python entry points не требуется.

---

## 6.3 Регистрация Connector'ов

В MVP используется статический реестр:

```python
from .explyt import ExplytConnector
from .kilo_code import KiloCodeConnector
from .zed import ZedConnector


CONNECTORS = {
    "zed": ZedConnector,
    "kilo_code": KiloCodeConnector,
    "explyt": ExplytConnector,
}
```

Функция получения реализации:

```python
def create_connector(
    name: str,
    *,
    template_root: Path,
) -> BaseConnector:
    connector_type = CONNECTORS.get(name)

    if connector_type is None:
        raise UnknownConnectorError(name)

    return connector_type(template_root=template_root)
```

Реестр является частью приложения и не редактируется пользователем.

---

## 6.4 Возможности Connector

Каждый Connector объявляет фактически поддерживаемые возможности.

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ConnectorCapabilities:
    skills: bool
    rules: bool
    mcp_prompts: bool = False
    additional_skill_files: bool = False
    rule_export_modes: tuple[str, ...] = ("separate",)
```

Пример:

```python
class ZedConnector(BaseConnector):
    name = "zed"
    label = "Zed"

    capabilities = ConnectorCapabilities(
        skills=True,
        rules=True,
        mcp_prompts=True,
        additional_skill_files=True,
        rule_export_modes=("instructions",),
    )
```

`mcp_prompts` является информационной возможностью целевой среды. Она не добавляет экспорт Prompt в Connector API.

---

## 6.5 Базовый интерфейс Connector

Рекомендуемый интерфейс:

```python
from abc import ABC, abstractmethod
from pathlib import Path
from typing import Any, Mapping, Sequence


class BaseConnector(ABC):
    name: str
    label: str
    capabilities: ConnectorCapabilities

    def __init__(self, template_root: Path) -> None:
        self.template_root = template_root

    @abstractmethod
    def validate_options(
        self,
        options: Mapping[str, Any],
    ) -> list[str]:
        """Возвращает список ошибок конфигурации Connector."""

    @abstractmethod
    def export_skill(
        self,
        item: SkillItem,
        context: ExportContext,
    ) -> list[ExportArtifact]:
        """Формирует целевые файлы для одного Skill."""

    @abstractmethod
    def export_rules(
        self,
        items: Sequence[RuleItem],
        context: ExportContext,
    ) -> list[ExportArtifact]:
        """Формирует целевые файлы для набора Rule."""

    def validate_target(
        self,
        context: ExportContext,
    ) -> list[str]:
        """Проверяет target и возвращает ошибки."""
        return []
```

Методы `export_skill()` и `export_rules()` не обязаны самостоятельно писать файлы. Они формируют список экспортных артефактов, которые затем безопасно записывает Export Engine.

Такой подход обеспечивает единый механизм для:

- dry-run;
- проверки конфликтов;
- вычисления статуса;
- атомарной записи;
- manifest;
- безопасного удаления.

---

## 6.6 Почему используется `export_rules()`

Для Skill достаточно обработки одного объекта:

```python
export_skill(item, context)
```

Rules могут экспортироваться двумя способами:

- каждый Rule в отдельный файл;
- все Rule в один агрегированный файл.

Поэтому базовый интерфейс принимает набор Rule:

```python
export_rules(items, context)
```

Connector самостоятельно выбирает способ представления в зависимости от:

- возможностей целевой IDE;
- значения `rule_export_mode`;
- проектных опций.

---

## 6.7 Контекст экспорта

Connector получает только необходимые для экспорта параметры.

```python
from dataclasses import dataclass, field
from pathlib import Path
from typing import Any


@dataclass(frozen=True)
class ExportContext:
    connector_name: str
    project_key: str
    target_dir: Path
    options: dict[str, Any] = field(default_factory=dict)
    dry_run: bool = False
```

Поля:

| Поле | Описание |
|---|---|
| `connector_name` | Имя Connector |
| `project_key` | Идентификатор проекта |
| `target_dir` | Разрешённый корневой target |
| `options` | Итоговые Connector и project options |
| `dry_run` | Признак предварительного просмотра |

Connector не должен изменять `ExportContext`.

---

## 6.8 Экспортный артефакт

Результат работы Connector представляется как `ExportArtifact`.

```python
from dataclasses import dataclass
from pathlib import Path


@dataclass(frozen=True)
class ExportArtifact:
    source_id: str
    source_type: str
    relative_target_path: Path
    content: str
    encoding: str = "utf-8"
```

Пример:

```python
ExportArtifact(
    source_id="python-review",
    source_type="skill",
    relative_target_path=Path(
        ".zed/skills/python-review/SKILL.md"
    ),
    content=rendered_content,
)
```

Требования:

- `relative_target_path` должен быть относительным;
- путь не может содержать выход через `..`;
- `source_type` принимает `skill` или `rule`;
- содержимое должно быть готово к записи;
- абсолютный target формирует только Export Engine.

---

## 6.9 Предупреждения и пропущенные объекты

Обычного списка файлов недостаточно для описания частично успешного экспорта. Поэтому Connector может возвращать результат с предупреждениями.

```python
from dataclasses import dataclass, field


@dataclass
class ConnectorExportResult:
    artifacts: list[ExportArtifact] = field(default_factory=list)
    warnings: list[str] = field(default_factory=list)
    skipped: list["SkippedItem"] = field(default_factory=list)


@dataclass(frozen=True)
class SkippedItem:
    source_id: str
    source_type: str
    reason: str
```

В этом случае сигнатуры могут выглядеть так:

```python
def export_skill(
    self,
    item: SkillItem,
    context: ExportContext,
) -> ConnectorExportResult:
    ...
```

```python
def export_rules(
    self,
    items: Sequence[RuleItem],
    context: ExportContext,
) -> ConnectorExportResult:
    ...
```

Этот вариант рекомендуется как основной.

---

## 6.10 Правила обработки объектов Connector'ом

Перед формированием артефакта Connector должен проверить:

- поддерживает ли он тип объекта;
- разрешён ли тип через `settings.yaml`;
- совместим ли объект с текущим Connector;
- поддерживаются ли выбранные export options;
- можно ли представить объект в целевом формате;
- нет ли конфликтов целевых относительных путей.

Общая валидация объекта выполняется до вызова Connector. Connector не должен повторно реализовывать все проверки YAML Frontmatter.

---

## 6.11 Фильтрация по `compatibility`

Export Engine выполняет первичную фильтрацию:

```yaml
compatibility:
  - zed
  - kilo_code
```

Если текущий Connector отсутствует в списке, объект пропускается.

Connector может выполнить дополнительную проверку, если конкретные свойства объекта несовместимы с целевой IDE.

Причина пропуска обязательно сохраняется в результате операции.

---

## 6.12 Работа с metadata

Connector получает полный словарь внутреннего frontmatter.

Он должен:

1. выбрать поддерживаемые поля;
2. при необходимости переименовать их;
3. добавить обязательные поля целевого формата;
4. удалить внутренние служебные поля;
5. сериализовать metadata детерминированно.

К внутренним полям, которые обычно не должны попадать в target без явной необходимости, относятся:

```text
compatibility
enabled
status
copy_mode
mcp_enabled
mcp_name
```

Connector не должен изменять `item.metadata` на месте.

Правильный подход:

```python
target_metadata = dict(item.metadata)
target_metadata.pop("compatibility", None)
target_metadata.pop("enabled", None)
```

---

## 6.13 Детерминированность экспорта

При одинаковых:

- исходных файлах;
- настройках;
- версии приложения;
- версии шаблонов;

Connector должен формировать одинаковый результат.

Поэтому запрещается без необходимости добавлять в экспортируемое содержимое:

- текущее время;
- случайные идентификаторы;
- абсолютные source-пути;
- нестабильный порядок metadata;
- данные текущей UI-сессии.

Время экспорта хранится только в manifest и журнале.

---

## 6.14 Jinja2 в Connector

Базовый Connector может предоставлять общий метод рендеринга:

```python
class BaseConnector(ABC):
    def render_template(
        self,
        template_name: str,
        *,
        item: ContextItem,
        metadata: dict[str, Any],
        context: ExportContext,
    ) -> str:
        ...
```

Контекст шаблона:

```text
item
metadata
body
title
description
tags
source_id
connector
project
options
```

Пример шаблона:

```jinja2
---
{{ metadata | to_yaml }}
---

{{ body }}
```

Для YAML необходимо зарегистрировать безопасный фильтр:

```python
def to_yaml(value: dict[str, Any]) -> str:
    return yaml.safe_dump(
        value,
        allow_unicode=True,
        sort_keys=False,
    ).strip()
```

Jinja autoescape для Markdown должен быть отключён.

---

## 6.15 Выбор шаблона

Для Skill:

```text
templates/<connector>/skill.md.j2
```

Для Rule:

```text
templates/<connector>/rule.md.j2
```

Для агрегированных Rules Connector может использовать:

```text
templates/<connector>/rules-aggregate.md.j2
```

Порядок поиска:

1. специализированный шаблон режима;
2. шаблон типа объекта;
3. `default.md.j2`;
4. Python fallback;
5. ошибка экспорта, если fallback отсутствует.

Пример:

```text
templates/kilo_code/rules-aggregate.md.j2
templates/kilo_code/rule.md.j2
templates/kilo_code/default.md.j2
```

---

## 6.16 Формирование целевых путей

Connector формирует только относительные пути.

Например:

```python
relative_target_path = Path(
    ".kilocode/skills"
) / item.relative_path
```

Export Engine формирует абсолютный путь:

```python
target_path = (
    context.target_dir / artifact.relative_target_path
).resolve()
```

После разрешения обязательно проверяется, что `target_path` остаётся внутри `context.target_dir`.

Connector не должен:

- возвращать абсолютный путь;
- использовать `..`;
- читать произвольный пользовательский путь из metadata;
- записывать файлы за пределами target.

---

## 6.17 Коллизии целевых путей

Несколько исходных объектов не должны формировать один и тот же target-файл, кроме явного агрегирования Rules.

Если возникает коллизия:

```text
source A → target/path.md
source B → target/path.md
```

Export Engine должен:

- остановить запись конфликтующих артефактов;
- добавить ошибку в результат;
- не выбирать один объект молча.

Для агрегированного файла все исходные Rule указываются в manifest как источники одного target.

---

## 6.18 Дополнительные файлы Skill

Если Connector поддерживает дополнительные Markdown-файлы:

```python
capabilities.additional_skill_files = True
```

он может сформировать несколько артефактов:

```text
SKILL.md
checklist.md
examples.md
```

Если дополнительные файлы не поддерживаются:

- основной `SKILL.md` экспортируется;
- остальные файлы пропускаются;
- в результат добавляется предупреждение.

Дополнительные файлы не должны автоматически объединяться с `SKILL.md`, если такое поведение явно не реализовано Connector.

---

## 6.19 Экспорт Rules отдельными файлами

Для режима:

```yaml
rule_export_mode: separate
```

каждый Rule преобразуется в отдельный `ExportArtifact`.

Порядок обхода:

1. `priority`;
2. относительный source-путь.

Пример результата:

```text
target/
└── rules/
    ├── architecture/
    │   └── dependency-direction.md
    └── python/
        └── strict-typing.md
```

Connector может сохранить исходную структуру или преобразовать её в нативную структуру IDE.

---

## 6.20 Агрегированный экспорт Rules

Для режима:

```yaml
rule_export_mode: aggregate
```

Connector формирует один файл.

Пример:

```markdown
# Project Rules

## Use pytest

Always use pytest for Python tests.

---

## Strict typing

All public Python functions must have type annotations.
```

Требования:

- порядок Rule детерминирован;
- заголовок каждого Rule берётся из `title`;
- источник каждого фрагмента отслеживается в manifest;
- пустые и невалидные Rule не включаются;
- между Rule используется предсказуемый разделитель;
- frontmatter итогового файла формируется Connector'ом.

---

## 6.21 Удаление экспортированных файлов

Connector не должен рекурсивно удалять весь `target_dir`.

Удаление выполняет Export Engine на основании manifest.

При необходимости Connector может предоставить дополнительные действия очистки:

```python
def cleanup_empty_directories(
    self,
    context: ExportContext,
    removed_paths: list[Path],
) -> list[str]:
    return []
```

Метод может удалять только пустые каталоги, созданные в рамках интеграции.

Каталоги с неизвестными пользовательскими файлами не удаляются.

---

## 6.22 Статус экспорта

Статус вычисляется сравнением:

- текущего набора ожидаемых `ExportArtifact`;
- manifest;
- фактических файлов в target.

Возможные состояния файла:

| Состояние | Описание |
|---|---|
| `synced` | Файл существует, checksum совпадает |
| `missing` | Ожидаемый файл отсутствует |
| `modified` | Файл существует, но содержимое отличается |
| `new` | Объект ещё не экспортировался |
| `stale` | Файл есть в manifest, но источник больше не экспортируется |
| `conflict` | Целевой файл существует, но не принадлежит текущему manifest |

Connector формирует ожидаемые артефакты, но сравнение checksum выполняет Export Engine.

---

## 6.23 Dry-run

Dry-run использует тот же Connector API, что и реальный экспорт.

Разница состоит только в том, что Export Engine:

- не создаёт каталоги;
- не записывает файлы;
- не обновляет manifest;
- не удаляет устаревшие файлы.

Connector не должен реализовывать отдельную ветку преобразования для dry-run. Это обеспечивает совпадение предварительного просмотра с реальным экспортом.

В результате dry-run отображаются:

- файлы, которые будут созданы;
- файлы, которые будут обновлены;
- конфликты;
- пропущенные объекты;
- предупреждения;
- устаревшие управляемые файлы.

---

## 6.24 Обработка ошибок

Ошибки Connector делятся на три уровня.

### Ошибка объекта

Пример:

- отсутствует обязательное поле для целевого формата;
- недопустимое имя;
- неподдерживаемое содержимое.

Остальные объекты продолжают обрабатываться.

### Ошибка проекта

Пример:

- некорректные project options;
- target не соответствует ожиданиям Connector;
- невозможно определить целевую структуру.

Экспорт текущего проекта прекращается.

### Ошибка Connector

Пример:

- отсутствует обязательный шаблон;
- внутренняя ошибка реализации;
- несовместимая версия API.

Операции этого Connector прекращаются, остальные Connector'ы могут продолжить работу.

---

## 6.25 Исключения Connector API

Рекомендуемые исключения:

```python
class ConnectorError(Exception):
    pass


class ConnectorConfigurationError(ConnectorError):
    pass


class UnsupportedCapabilityError(ConnectorError):
    pass


class ConnectorRenderError(ConnectorError):
    pass


class InvalidTargetPathError(ConnectorError):
    pass


class ExportConflictError(ConnectorError):
    pass
```

Пользовательский интерфейс не должен показывать необработанный traceback вместо понятного сообщения.

Полный traceback допускается записывать в debug-лог.

---

## 6.26 Zed Connector

Zed Connector должен поддерживать:

```python
skills = True
rules = True
mcp_prompts = True
```

Смысл возможностей:

- Skills экспортируются в нативную структуру Zed Skills;
- Rules экспортируются в механизм Zed Instructions;
- Prompts не экспортируются, но Zed может подключаться к MCP Server.

Пример декларации:

```python
class ZedConnector(BaseConnector):
    name = "zed"
    label = "Zed"

    capabilities = ConnectorCapabilities(
        skills=True,
        rules=True,
        mcp_prompts=True,
        additional_skill_files=True,
        rule_export_modes=("instructions",),
    )
```

Точные целевые относительные пути и формат metadata должны быть реализованы согласно актуальной документации Zed и изолированы внутри `zed.py`.

## 6.27 Kilo Code Connector

Kilo Code Connector должен поддерживать:

```python
skills = True
rules = True
mcp_prompts = False
```

Пример:

```python
class KiloCodeConnector(BaseConnector):
    name = "kilo_code"

        skills=True,
```

Connector отвечает за:

- нативную структуру Kilo Code Skills;
- требуемое metadata Skill;
- экспорт Custom Rules;
- поддерживаемый способ объединения Rule, если он выбран.

Prompt Library не участвует в этом Connector.

## 6.29 Неизвестные поля целевого формата

```python
allowed_fields = {

}
```

В целевой frontmatter попадают:

- разрешённые внутренние поля;
- обязательные поля, добавленные Connector;
- явно настроенные дополнительные поля, если они поддерживаются.

Не рекомендуется безусловно копировать весь внутренний frontmatter, поскольку IDE-specific parser может не поддерживать неизвестные поля.

## 6.30 Минимальный пример Connector

```python
class ExampleConnector(BaseConnector):
    name = "example"
    label = "Example IDE"

    capabilities = ConnectorCapabilities(
        skills=True,
        rules=True,
        rule_export_modes=("separate",),
    )

    def validate_options(
        self,
        options: Mapping[str, Any],
    ) -> list[str]:
        errors: list[str] = []

        mode = options.get("rule_export_mode", "separate")
        if mode not in self.capabilities.rule_export_modes:
            errors.append(f"Unsupported rule export mode: {mode}")

        return errors

    def export_skill(
        self,
        item: SkillItem,
        context: ExportContext,
    ) -> ConnectorExportResult:
        metadata = {
            "title": item.metadata["title"],
            "description": item.metadata["description"],
        }

        content = self.render_template(
            "skill.md.j2",
            item=item,
            metadata=metadata,
            context=context,
        )

        artifact = ExportArtifact(
            source_id=item.relative_path.parent.as_posix(),
            source_type="skill",
            relative_target_path=(
                Path(".example/skills")
                / item.relative_path.parent
                / "SKILL.md"
            ),
            content=content,
        )

        return ConnectorExportResult(
            artifacts=[artifact],
        )

    def export_rules(
        self,
        items: Sequence[RuleItem],
        context: ExportContext,
    ) -> ConnectorExportResult:
        artifacts: list[ExportArtifact] = []

        for item in sorted(
            items,
            key=lambda value: (
                value.priority,
                value.relative_path.as_posix(),
            ),
        ):
            artifacts.append(
                ExportArtifact(
                    source_id=item.relative_path.with_suffix("").as_posix(),
                    source_type="rule",
                    relative_target_path=(
                        Path(".example/rules")
                        / item.relative_path
                    ),
                    content=item.body,
                )
            )

        return ConnectorExportResult(artifacts=artifacts)
```

## 6.31 Границы Connector API в MVP

В MVP Connector API не включает:

- импорт данных из IDE;
- автоматическое обнаружение IDE;
- установку IDE или расширений;
- изменение конфигурации IDE;
- запуск внешних команд;
- сетевые операции;
- публикацию Prompt'ов;
- MCP Tools и Resources;
- сторонние Connector packages;
- версионирование API для внешних разработчиков.

Connector — это простой внутренний адаптер одностороннего файлового экспорта Skills и Rules.

# Часть 7. Export Engine

## 7.1 Назначение

Export Engine координирует односторонний экспорт Skills и Rules из Context Repository в целевые каталоги IDE.

Export Engine отвечает за:

- загрузку и проверку конфигурации;
- выбор Connector и проекта;
- загрузку Skills и Rules;
- фильтрацию объектов;
- получение `ExportArtifact` от Connector;
- проверку конфликтов;
- dry-run;
- безопасную запись файлов;
- формирование manifest;
- вычисление статуса;
- удаление ранее экспортированных файлов;
- журналирование результатов.

Prompts никогда не передаются в Export Engine.

---

## 7.2 Основные операции

```python
class ExportEngine:
    def export(
        self,
        connector_name: str,
        project_key: str,
        *,
        dry_run: bool = False,
    ) -> ExportResult:
        ...

    def export_all(
        self,
        project_key: str | None = None,
        *,
        dry_run: bool = False,
    ) -> list[ExportResult]:
        ...

    def get_status(
        self,
        connector_name: str,
        project_key: str,
    ) -> ExportStatus:
        ...

    def delete_exported(
        self,
        connector_name: str,
        project_key: str,
    ) -> DeleteResult:
        ...
```

Реализация может быть синхронной внутри сервисного слоя. Вызов блокирующих файловых операций из Reflex State должен выполняться через фоновые задачи или `asyncio.to_thread()`.

---

## 7.3 Результат экспорта

```python
@dataclass
class ExportResult:
    connector_name: str
    project_key: str
    dry_run: bool

    created: list[Path] = field(default_factory=list)
    updated: list[Path] = field(default_factory=list)
    unchanged: list[Path] = field(default_factory=list)
    skipped: list[SkippedItem] = field(default_factory=list)
    stale: list[Path] = field(default_factory=list)
    conflicts: list[Path] = field(default_factory=list)
    warnings: list[str] = field(default_factory=list)
    errors: list[str] = field(default_factory=list)

    @property
    def is_success(self) -> bool:
        return not self.errors and not self.conflicts
```

Операция может быть частично успешной: ошибка одного объекта не обязана блокировать обработку остальных, если она не влияет на целостность проекта.

---

## 7.4 Алгоритм экспорта

Для одного Connector и проекта:

1. Загрузить актуальную конфигурацию.
2. Проверить, что Connector и проект существуют и включены.
3. Объединить Connector и project options.
4. Создать `ExportContext`.
5. Проверить возможности и опции Connector.
6. Загрузить Skills и Rules из Context Repository.
7. Исключить:
   - невалидные объекты;
   - `enabled: false`;
   - объекты со статусом, отличным от `active`;
   - объекты, несовместимые с Connector;
   - типы, отключённые в `supports`.
8. Передать Skills в `export_skill()`.
9. Передать отсортированный набор Rules в `export_rules()`.
10. Объединить полученные артефакты.
11. Проверить целевые пути и коллизии.
12. Загрузить существующий manifest.
13. Классифицировать изменения.
14. В режиме dry-run вернуть план без записи.
15. В обычном режиме атомарно записать разрешённые файлы.
16. Обновить manifest.
17. Вернуть структурированный результат.
18. Добавить запись в журнал операций.

---

## 7.5 Классификация целевых файлов

Перед записью каждый артефакт классифицируется:

| Состояние | Условие |
|---|---|
| `create` | Файл отсутствует |
| `update` | Файл управляется текущим manifest, но содержимое изменилось |
| `unchanged` | Файл существует и checksum совпадает |
| `conflict` | Файл существует, но не принадлежит manifest |
| `blocked` | Перезапись запрещена настройкой `overwrite` |

Режим `overwrite` применяется следующим образом:

### `managed_only`

- управляемые файлы можно обновлять;
- неизвестные существующие файлы считаются конфликтом.

### `always`

- существующие файлы можно перезаписывать;
- в результат добавляется предупреждение.

### `never`

- любой существующий изменяемый файл блокирует запись.

---

## 7.6 Поведение при конфликтах

По умолчанию конфликтующий файл не перезаписывается.

Экспорт остальных независимых файлов может продолжиться, но операция считается частично неуспешной.

UI должен показать:

- целевой путь;
- исходный объект;
- причину конфликта;
- текущий режим `overwrite`.

В MVP не требуется интерактивное разрешение конфликтов с просмотром diff.

---

## 7.7 Manifest

Manifest является служебным источником информации о файлах, созданных приложением.

Рекомендуемый путь:

```text
<target_dir>/.context-desk/<connector>/<project>/manifest.json
```

Если конкретный `target_dir` уже уникален для Connector и проекта, допускается сокращённый путь. Однако структура должна исключать перезапись manifest другого проекта.

Manifest должен содержать:

```json
{
  "schema_version": 1,
  "connector": "kilo_code",
  "project": "project_x",
  "exported_at": "2026-08-07T14:30:00Z",
  "application_version": "1.0.0",
  "files": [
    {
      "target_path": ".kilocode/skills/python-review/SKILL.md",
      "sha256": "...",
      "sources": [
        {
          "id": "python-review",
          "type": "skill"
        }
      ]
    }
  ]
}
```

Все пути внутри manifest должны быть относительными к `target_dir`.

---

## 7.8 Обновление manifest

Manifest обновляется только после завершения записи файлов.

Он должен содержать фактически успешно записанные или подтверждённые неизменными файлы.

Файлы, для которых возникли:

- ошибки;
- конфликты;
- запрет перезаписи;

не включаются как успешно обновлённые.

Запись manifest выполняется атомарно.

---

## 7.9 Устаревшие файлы

Файл считается `stale`, если:

- он присутствует в предыдущем manifest;
- новый план экспорта больше его не содержит.

Причины:

- исходный объект удалён;
- объект отключён;
- изменилась `compatibility`;
- изменился целевой путь;
- отключена соответствующая capability.

В MVP устаревшие файлы не удаляются автоматически при обычном экспорте. Они:

- показываются в результате;
- могут быть удалены отдельной командой **Clean stale** или **Delete exported**.

Это снижает риск неожиданного удаления данных.

---

## 7.10 Удаление экспортированных файлов

Операция `delete_exported()`:

1. загружает manifest;
2. проверяет все целевые пути;
3. удаляет только перечисленные в manifest файлы;
4. не следует по символическим ссылкам;
5. удаляет пустые служебные каталоги;
6. удаляет manifest после успешной очистки;
7. возвращает список удалённых, отсутствующих и ошибочных файлов.

Если содержимое управляемого файла было изменено после экспорта, UI должен предупредить пользователя.

По умолчанию изменённый файл не удаляется без явного подтверждения.

---

## 7.11 Статус экспорта

`get_status()` строит ожидаемые артефакты без записи и сравнивает их с target и manifest.

```python
@dataclass
class ExportStatus:
    synced: list[Path] = field(default_factory=list)
    new: list[Path] = field(default_factory=list)
    modified: list[Path] = field(default_factory=list)
    missing: list[Path] = field(default_factory=list)
    stale: list[Path] = field(default_factory=list)
    conflicts: list[Path] = field(default_factory=list)
    errors: list[str] = field(default_factory=list)
```

Операция статуса не изменяет файловую систему.

---

## 7.12 Export All

`export_all()` обрабатывает:

- все включённые Connector'ы;
- все включённые проекты либо указанный проект, если такой ключ существует;
- только разрешённые capabilities.

Ошибка одного Connector не должна останавливать остальные Connector'ы.

Итоговый результат содержит отдельную запись для каждой пары:

```text
Connector + Project
```

---

## 7.13 Параллельность и блокировки

В MVP достаточно следующих ограничений:

- для одной пары Connector + Project одновременно выполняется не более одной изменяющей операции;
- повторный экспорт блокируется до завершения текущего;
- статус и dry-run могут быть сериализованы с экспортом для упрощения;
- MCP Server работает независимо, поскольку читает только Prompts.

Глобальная параллельная запись в несколько target-каталогов не является обязательной.

---

# Часть 8. Prompt Manager и MCP Server

## 8.1 Prompt Manager

Prompt Manager отвечает за:

- сканирование `prompts/**/*.md`;
- парсинг frontmatter;
- валидацию Prompt;
- формирование MCP-имён;
- обнаружение дубликатов;
- фильтрацию по статусу и тегам;
- подготовку содержимого для Clipboard;
- предоставление Prompt'ов MCP Server.

Prompt Manager не зависит от Connector'ов и Export Engine.

---

## 8.2 Интерфейс Prompt Manager

```python
class PromptManager:
    def list_prompts(
        self,
        *,
        include_inactive: bool = False,
    ) -> list[PromptItem]:
        ...

    def get_prompt(self, prompt_id: str) -> PromptItem:
        ...

    def get_by_mcp_name(self, name: str) -> PromptItem:
        ...

    def get_copy_content(self, prompt_id: str) -> str:
        ...

    def refresh(self) -> list[PromptItem]:
        ...
```

Prompt Manager может использовать простой in-memory cache. Файловая система остаётся источником истины.

---

## 8.3 Публикуемые MCP Prompts

Через MCP публикуются только Prompt'ы, которые:

- валидны;
- имеют `enabled: true`;
- имеют `mcp_enabled: true`;
- имеют `status: active`;
- имеют уникальное MCP-имя.

Черновики, архивные и невалидные Prompt'ы не должны попадать в `prompts/list`.

---

## 8.4 MCP-операции MVP

Встроенный MCP Server должен поддерживать Prompt capability:

- `prompts/list`;
- `prompts/get`.

MCP Tools и Resources не входят в MVP.

Представление Prompt в UI конкретного MCP-клиента определяется самим клиентом. Приложение гарантирует корректную публикацию через MCP, но не управляет отображением slash-команд в IDE.

---

## 8.5 Формирование ответа MCP

Для каждого Prompt сервер предоставляет:

- имя;
- описание;
- содержимое Markdown body.

Если `mcp_name` не указан, имя формируется из относительного пути.

В MVP Prompt не имеет аргументов:

```text
arguments = []
```

Тело `prompts/get` возвращается как пользовательское сообщение с текстовым содержимым в формате, поддерживаемом используемой версией MCP SDK/FastMCP.

---

## 8.6 Жизненный цикл MCP Server

MCP Server является встроенной подсистемой приложения.

Он должен запускаться:

- после успешной загрузки конфигурации;
- только если `mcp.enabled: true`;
- только после успешной инициализации Prompt Manager.

Он должен останавливаться:

- при завершении приложения;
- при отключении MCP через Settings;
- перед изменением host, port или path;
- при критической ошибке конфигурации.

Не следует запускать MCP Server непосредственно во время импорта Python-модуля или создания `rx.App`. Запуск должен выполняться через управляемый lifecycle приложения.

---

## 8.7 Совместное выполнение с Reflex

Рекомендуется запускать MCP Server как отдельную управляемую асинхронную задачу в процессе backend приложения, если используемая версия Reflex и FastMCP позволяет корректно управлять lifecycle.

```text
Backend process
├── Reflex backend
└── FastMCP task
```

Если совместный event loop технически несовместим с выбранными версиями библиотек, допускается запуск дочернего процесса через единый application launcher. Для пользователя это всё равно остаётся одним приложением и одной командой запуска.

Конкретный вариант фиксируется после короткого технического прототипа.

---

## 8.8 Состояния MCP Server

```text
disabled
starting
running
stopping
stopped
error
```

State должен содержать:

- текущее состояние;
- endpoint;
- время запуска;
- последнее сообщение об ошибке.

Ошибка MCP не должна блокировать File Manager или Export Engine.

---

## 8.9 MCP endpoint

Для конфигурации:

```yaml
mcp:
  transport: streamable_http
  host: "127.0.0.1"
  port: 8080
  path: "/mcp"
```

UI показывает endpoint:

```text
http://127.0.0.1:8080/mcp
```

Приложение не должно автоматически изменять конфигурацию IDE пользователя.

В UI может отображаться готовый пример настройки подключения, который пользователь копирует вручную.

---

## 8.10 Кэш и актуальность

При `refresh_on_request: true` Prompt Manager обновляет индекс перед MCP-запросом.

Для снижения лишнего чтения допускается оптимизация по:

- `mtime`;
- размеру файла;
- короткому TTL.

Однако преждевременная сложная система наблюдения за файлами не требуется.

Ошибка одного Prompt не должна блокировать публикацию остальных.

---

## 8.11 Безопасность MCP

MVP не реализует аутентификацию и TLS.

Поэтому:

- значение host по умолчанию — `127.0.0.1`;
- внешний host сопровождается предупреждением;
- содержимое Prompt не пишется полностью в обычный журнал;
- ошибки не должны раскрывать лишние абсолютные пути MCP-клиенту;
- path traversal через MCP-имя запрещён;
- клиент не может передавать путь к произвольному файлу.

---

## 9.2 Dashboard

### Connector Overview

Для каждого включённого Connector:

- название;

# Часть 10. State Management

## 10.1 Структура State

Для MVP допустим единый State, но рекомендуется разделить его на несколько логических классов:

```text
AppState
├── RepositoryState
├── EditorState
├── PromptState
├── ExportState
├── McpState
└── SettingsState
```

Если наследование или композиция State усложняет работу с конкретной версией Reflex, допускается один `AppState` с чётко сгруппированными полями.

## 10.4 Обработка блокирующих операций

Обычные операции `pathlib`, PyYAML и Jinja2 являются синхронными.

Чтобы не блокировать Reflex backend при продолжительной операции, вызовы сервисов выполняются через:

```python
result = await asyncio.to_thread(
    service_method,
    ...
)
```

Не требуется делать каждую небольшую функцию файловой системы `async`.

Асинхронность должна применяться на уровне event handler и orchestration.

---

## 10.5 Dirty State редактора

При изменении текста:

```text
file_dirty = true
```

При успешном сохранении:

```text
file_dirty = false
```

При выборе другого файла с несохранёнными изменениями UI должен запросить подтверждение.

Автосохранение не входит в MVP.

---

## 10.6 Ошибки State

Event handler должен:

1. установить operation flag;
2. выполнить сервисную операцию;
3. преобразовать результат в сериализуемое состояние;
4. показать toast;
5. сбросить operation flag в `finally`.

Необработанные исключения не должны оставлять UI в состоянии бесконечной загрузки.

# Часть 11. Основные Use Cases

## UC-1. Запуск приложения

1. Пользователь запускает `just dev` или `just run`.
2. Загружается `settings.yaml`.
3. Валидируется конфигурация.
4. Инициализируется Context Repository.
5. Сканируются Skills, Rules и Prompts.
6. При необходимости запускается MCP Server.
7. Открывается Dashboard.
8. Ошибки отображаются без полного падения UI, если это возможно.

---

## UC-2. Создание Skill

1. Пользователь открывает `/files`.
2. Нажимает **New Skill**.
3. Вводит путь, title и description.
4. Приложение проверяет путь.
5. Создаётся `<path>/SKILL.md`.
6. Файл открывается в редакторе.
7. Skill получает статус `draft`.

---

## UC-3. Редактирование объекта

1. Пользователь выбирает файл.
2. Приложение загружает исходный текст.
3. Пользователь изменяет Markdown.
4. Нажимает Save.
5. Выполняется парсинг и валидация.
6. Файл сохраняется атомарно.
7. UI обновляет metadata и ошибки.
8. Для Prompt обновляется MCP cache.

Невалидный объект разрешается сохранить, но он не экспортируется и не публикуется.

---

## UC-4. Экспорт Connector

1. Пользователь выбирает Connector и проект.
2. Нажимает **Export**.
3. UI блокирует повторный запуск.
4. Export Engine формирует план.
5. Выполняются проверки конфликтов.
6. Файлы записываются атомарно.
7. Обновляется manifest.
8. Показывается итоговый результат.

---

## UC-5. Dry-run

1. Пользователь нажимает **Dry-run**.
2. Формируются те же артефакты, что и при экспорте.
3. Файловая система не изменяется.
4. UI показывает создаваемые, обновляемые, конфликтующие и stale-файлы.

---

## UC-6. Проверка статуса

1. Пользователь нажимает **Status**.
2. Формируется ожидаемый результат экспорта.
3. Проверяются target-файлы и manifest.
4. UI показывает `synced`, `new`, `modified`, `missing`, `stale` и `conflict`.

---

## UC-7. Удаление экспортированных файлов

1. Пользователь нажимает **Delete exported**.
2. UI показывает подтверждение.
3. Export Engine загружает manifest.
4. Изменённые после экспорта файлы требуют отдельного подтверждения.
5. Удаляются только управляемые файлы.
6. Удаляется manifest.
7. Отображается результат.

---

## UC-8. Копирование Prompt

1. Пользователь открывает `/prompts`.
2. Находит Prompt.
3. Нажимает **Copy**.
4. Prompt Manager читает актуальный объект.
5. Выбирается body или full content.
6. Текст копируется в Clipboard.
7. Отображается toast.

---

## UC-9. Получение Prompt через MCP

1. MCP-клиент подключается к endpoint.
2. Запрашивает список Prompt'ов.
3. Prompt Manager возвращает активные валидные объекты.
4. Клиент запрашивает Prompt по имени.
5. Сервер возвращает его содержимое.
6. Невалидный или неизвестный Prompt возвращает протокольную ошибку без раскрытия filesystem path.

---

## UC-10. Изменение MCP Settings

1. Пользователь изменяет host, port или enabled.
2. Настройки валидируются и сохраняются.
3. Текущий MCP Server останавливается.
4. Сервер запускается с новой конфигурацией, если он включён.
5. UI обновляет endpoint и статус.
6. При ошибке остальная часть приложения продолжает работать.

---

# Часть 12. Техническая архитектура

## 12.1 Технологический стек

- Python 3.11+;
- Reflex;
- PyYAML;
- Jinja2;
- FastMCP или совместимая актуальная Python-реализация MCP;
- Uvicorn в составе web stack;
- `uv` для управления зависимостями;
- `just` как task runner.

Перед реализацией версии библиотек фиксируются в `pyproject.toml` и `uv.lock`.

---

## 12.2 Зависимости модулей

```text
Reflex UI / State
        |
        +-----------------------+
        |                       |
        v                       v
File Manager              Export Engine
        |                       |
        v                       v
Context Models            Connectors
        |
        v
Prompt Manager
        |
        v
MCP Server
```

Ограничения:

- модели не зависят от Reflex;
- Connector'ы не зависят от State;
- MCP Server не зависит от Export Engine;
- File Manager не зависит от конкретной IDE.

---

## 12.3 Команды `just`

Минимальный `justfile`:

```just
install:
    uv sync

dev:
    uv run reflex run

run:
    uv run reflex run --env prod

format:
    uv run ruff format .

lint:
    uv run ruff check .

check:
    uv run ruff format --check .
    uv run ruff check .
```

Если MCP запускается через единый launcher, `just dev` должен поднимать обе подсистемы без второй ручной команды.

---

## 12.4 Логирование

Используется стандартный модуль `logging`.

Журналируются:

- запуск приложения;
- загрузка конфигурации;
- экспорт;
- удаление;
- конфликты;
- запуск и остановка MCP;
- ошибки парсинга;
- исключения сервисов.

По умолчанию не журналируются полностью:

- тела Prompt;
- содержимое Skills и Rules;
- потенциально чувствительные пользовательские данные.

UI-журнал хранится в памяти и ограничивается `max_log_entries`.

---

## 12.5 Обработка ошибок

Сервисный слой использует типизированные исключения и структурированные результаты.

На границе UI:

- техническая ошибка преобразуется в понятное сообщение;
- подробности пишутся в debug-лог;
- State возвращается в непротиворечивое состояние.

Ошибка отдельного файла не должна приводить к завершению всего приложения.

---

## 12.6 Поддерживаемые платформы

Основная цель MVP:

- Linux;
- WSL.

Поддержка macOS и Windows желательна благодаря `pathlib`, но не является обязательным критерием первой версии.

Нельзя жёстко кодировать Linux-разделители путей в Python-коде.

# Часть 13. Нефункциональные требования

## 13.1 Производительность

Приложение должно комфортно работать с репозиторием примерно до:

- 1 000 Markdown-файлов;
- 20 МБ общего текстового содержимого;
- 100 Connector/project combinations.

Целевые показатели для типичного локального репозитория:

- открытие Dashboard — до 2 секунд;
- обновление списка Prompt'ов — до 1 секунды;
- dry-run для сотен объектов — до нескольких секунд;
- копирование Prompt — без заметной задержки.

Это ориентиры, а не жёсткие SLA.

---

## 13.2 Надёжность

- исходные файлы не изменяются при экспорте;
- запись выполняется атомарно;
- удаление производится только по manifest;
- dry-run не изменяет файловую систему;
- частичная ошибка отражается в результате;
- при падении приложения существующие target-файлы не должны оставаться частично записанными.

---

## 13.3 Безопасность

- приложение по умолчанию доступно только локально;
- MCP слушает loopback;
- path traversal блокируется;
- YAML разбирается только через `safe_load`;
- Jinja-шаблоны не получают произвольный доступ к filesystem;
- Connector не запускает shell-команды;
- пользовательские Markdown-файлы не исполняются;
- HTML в Preview должен обрабатываться безопасно средствами Markdown-компонента.

---

## 13.4 Поддерживаемость

- код разбит на небольшие модули;
- IDE-specific логика находится в Connector;
- отсутствуют DI-контейнеры и сложные framework abstractions;
- публичные сервисные методы имеют type hints;
- форматирование и lint выполняются автоматически;
- важные решения документируются рядом с кодом или в README.

---

- [ ] Исходные файлы при экспорте не изменяются.

## 14.8 UI и журналирование

- [ ] Все длительные операции имеют progress state.
- [ ] Повторный запуск изменяющей операции блокируется.
- [ ] Успехи и ошибки показываются через toast.
- [ ] Подробные результаты доступны в UI.
- [ ] Журнал ограничивается заданным числом записей.
- [ ] Тела пользовательских объектов не записываются в обычный лог.

# Часть 15. Вне MVP и дальнейшее развитие

Следующие возможности сознательно не входят в MVP:

- двусторонняя синхронизация;
- импорт из IDE;
- автоматическое обнаружение IDE;
- автоматическое изменение IDE config;
- Git-интеграция;
- история изменений;
- versioning объектов;
- совместная работа;
- авторизация;
- облачное хранение;
- полнотекстовый поиск;
- Prompt variables и формы аргументов;
- Jinja-шаблонизация Prompt;
- MCP Tools;
- MCP Resources;
- REST API;
- stdio transport;
- SSE как legacy transport;
- внешние Connector packages;
- Marketplace;
- Obsidian, PDF и другие форматы публикации;
- watcher файловой системы;
- бинарные вложения;
- scripts внутри Skills;
- Monaco или CodeMirror;
- автоматическое разрешение конфликтов;
- отображение diff;
- резервные копии target-файлов.

Эти возможности могут быть добавлены позднее только при наличии практической потребности. Архитектура MVP не должна заранее реализовывать универсальный Publisher Framework или сложную доменную платформу.

# Итоговая архитектура MVP

```text
                   Context Desk
                            |
          +-----------------+-----------------+
          |                 |                 |
          v                 v                 v
     File Manager      Export Engine     Prompt Manager
          |                 |                 |
          |        +--------+--------+        |
          |        |        |        |        |
          |        v        v        v        v
          |       Zed     Kilo     Explyt   Clipboard
          |    Connector Connector Connector   |
          |                                     
          |                               FastMCP Server
          |                                      |
          +------------------+------------------+
                             |
                             v
                  Context Repository
                  ├── skills/
                  ├── rules/
                  └── prompts/
```

MVP остаётся небольшим локальным файловым приложением:

- Skills и Rules экспортируются в IDE через простые Connector'ы;
- Prompts используются через UI и MCP;
- Context Repository является единственным источником истины;
- никакой двусторонней синхронизации или универсальной платформы управления знаниями не создаётся.
