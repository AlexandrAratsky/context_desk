# Стратегия использования инструментов

Черновик правил выбора инструментов. Цель: меньше лишних действий, больше проверяемых результатов.

## Базовый порядок

1. Уточнить задачу, ограничения и необходимость подтверждения плана.
2. Выбрать самый узкий инструмент: IDE-native, MCP, агент, форк или терминал.
3. Перед правкой прочитать целевые файлы.
4. Внести минимальные изменения.
5. Проверить результат тестом, запуском, инспекцией, поиском или статическим анализом.
6. Кратко ответить: что изменено, где, чем проверено.

## Приоритет инструментов

1. **Нативные инструменты агента и IDE**: чтение, поиск, refactor, run/test, точечные правки.
2. **Serena MCP**: Python-first навигация, структура проекта, символы, семантический поиск.
3. **Специализированные MCP**: `Analyzer`, `UV`, `GitHub`, `DeepWiki`, `WebSearch`.
4. **Files MCP**: файловые операции, когда нужны пакетность, дерево, архивы или медиа.
5. **Terminal**: крайний вариант. Команду сначала показать пользователю и получить подтверждение.

## Делегирование

- `self_fork`: дешёвое параллельное исследование проекта, когда нужен итог без подробного следа.
- `call_code_agent`: код по чёткому заданию.
- `call_ask_agent`: исследование без правок.
- `call_review_agent`: полноценное ревью PR, diff или набора файлов.
- `call_plan_agent`: планирование до сложных изменений.
- `call_debug_agent`: runtime-отладка и debugger.
- `call_test_agent`: генерация или усиление тестов.

Для небольших последовательных задач делегирование не нужно.

## Навыки

Перед задачей проверить релевантные навыки через `use_skill` и применять их инструкции:

- `code-review-orchestrated`: ревью кода, PR, diff, коммита, ветки или файлов;
- `refactor-code`: рефакторинг с IDE-инструментами.

## Чтение, поиск и правки

- `list_dir`: обзор структуры, глубина обычно до 4.
- `search_file_by_name`: поиск файлов по имени или glob.
- `search_for_text`: точный текст, line anchors, grep-проверки.
- `similar_search`: смысловой поиск, когда неизвестны имена символов.
- `file_structure`: структура больших или неизвестных по размеру исходников.
- `read_file`: чтение файла диапазонами; для файлов больше 250 строк сначала `file_structure`.
- `find_symbol_source`: поиск объявления символа, для Python лучше FQN.
- `find_usages`: все использования символа, особенно перед удалением или переименованием.
- `write_file`: создание или полная перезапись; при создании `allow_overwrite=false`.
- `edit_file`: точечная правка после перечитывания файла.
- `rename_symbol`: IDE-переименование символа; после успеха не делать ручную замену ссылок.

## Запуск и проверка

- `get_configurations`: первый шаг для build/test/run/debug.
- `run_configuration`: запуск через IDE, выбирать самую узкую конфигурацию.
- `manage_background_run`: снимок или остановка фонового IDE-запуска.
- `run_command`: только если IDE/MCP не подходят и пользователь подтвердил команду.
- `read_terminal`: чтение вывода подтверждённой терминальной команды.

## Внешние источники

- `web_fetch`: чтение конкретных URL или PDF; перед ним предпочитать профильный MCP или CLI.
- `developer_platform_search`: StackOverflow, Wikipedia, GitHub. Нет результата значит только «не найдено там».

## MCP-серверы

### Общее правило выбора MCP

MCP использовать не как запасной способ сделать то же самое, а когда он даёт более точный, безопасный или специализированный доступ.

Если одну операцию умеют несколько MCP, выбирать по смыслу задачи:

1. Python-семантика и структура: `Serena`.
2. Python-анализ и форматирование: `Analyzer`.
3. Python-окружение и зависимости: `UV`.
4. IDE-диагностика, конфигурации, refactor: `IDE`.
5. Файловые операции без семантики: `Files`.
6. Внешняя проектная информация: `GitHub`, `DeepWiki`, `WebSearch`.

### Serena MCP

Приоритетный MCP для Python-проектов и задач, где важна структура кода.

Использовать для:

- обзора символов и модулей;
- поиска объявлений, реализаций и ссылок;
- семантического поиска по паттернам;
- навигации по Python-коду без грубого текстового поиска;
- точечных символьных правок, когда это безопаснее текстовой замены;
- диагностики по файлу, если нужна Python-aware проверка.

Почему выше Files MCP:

- понимает символы, а не только строки;
- лучше подходит для Python-навигации;
- снижает риск править не тот участок;
- помогает проверять структуру проекта без запуска shell-команд.

Не использовать как единственный источник истины после правок: результат надо подтверждать чтением файла, диагностикой, тестом или поиском.

### Analyzer MCP

Использовать для Python-статического анализа:

- `ruff-check`, `ruff-check-ci`: lint;
- `ruff-format`: форматирование;
- `ty-check`: проверка типов;
- `vulture-scan`: поиск мёртвого кода.

Приоритет выше терминала, потому что вызов уже ограничен доменной задачей и не требует произвольной shell-команды.

### UV MCP

Использовать для Python/uv задач:

- синхронизация окружения;
- управление зависимостями;
- lock/build;
- диагностика uv и Python;
- запуск скриптов через uv, если это безопаснее терминала.

Не добавлять и не удалять зависимости без подтверждённого решения.

### IDE MCP

Использовать, когда нужен доступ к возможностям IDE через MCP:

- диагностика файла;
- run configurations;
- зависимости проекта;
- символы и refactor;
- поиск по проекту;
- открытие файлов в редакторе.

Если такая же операция есть как нативный инструмент агента, сначала использовать нативный инструмент.

### Files MCP

Использовать для файловых операций без семантики кода:

- пакетное чтение нескольких файлов;
- дерево директорий;
- размеры, дубликаты, пустые папки;
- архивы zip/unzip;
- медиафайлы;
- простые create/edit/write, когда IDE-инструменты не дают преимущества.

Не выбирать Files MCP для Python-символов, refactor или анализа вызовов. Там приоритет у Serena или IDE.

### GitHub MCP

Использовать для GitHub как источника истины:

- PR, issues, commits, branches;
- releases и tags;
- code search по GitHub;
- данные репозитория, недоступные локально.

Предпочитать GitHub MCP внешнему поиску и терминальному `gh`, если MCP покрывает задачу.

### DeepWiki MCP

DeepWiki генерирует подробную документацию по GitHub-репозиториям и даёт поиск по данным проекта через Deep Research.

Использовать для чтения структуры этой документации и ответов по ней, когда пользователь ссылается на DeepWiki или wiki проекта.

### WebSearch MCP

WebSearch MCP даёт базовый поиск в интернете через DuckDuckGo и получение найденных страниц.

Использовать для внешнего веб-поиска, когда нет более точного источника.

### Files vs IDE vs Serena для редактирования

Приоритет редактирования:

1. `rename_symbol` или IDE refactor, если меняется символ.
2. `edit_file`, если нужна точечная текстовая правка.
3. Serena MCP, если правка символная или Python-aware и нативных инструментов недостаточно.
4. Files MCP, если правка файловая и не требует понимания кода.
5. `write_file`, если создаётся новый файл или нужна полная перезапись.

После любой правки перечитать изменённый участок и запустить доступную проверку.

## Terminal

Терминал использовать как можно реже.

Причины:

- произвольная shell-команда шире по правам, чем специализированный инструмент;
- выше риск разрушительных действий;
- сложнее гарантировать воспроизводимость и безопасность;
- build/test через терминал хуже IDE-конфигураций, если они доступны.

Правило:

1. Сначала искать нативный инструмент, MCP или IDE-конфигурацию.
2. Если нужен терминал, показать пользователю точную команду.
3. Объяснить, зачем она нужна и почему альтернативы не подходят.
4. Запускать только после подтверждения.
5. Не запускать потенциально опасные команды автоматически.

Исключение: явно безопасные read-only команды можно рассматривать только когда они не заменяют IDE/MCP. Для этого документа базовая политика строже: лучше спросить.

## Память

- `read_memory`: читать релевантную память перед обычными инструментами.
- `save_memory`: сохранять только долговременные неочевидные знания.
- `update_memory`: обновлять существующую память после чтения.
- `delete_memory`: удалять целую запись; для частичного забывания использовать `update_memory`.

## Ревью

`proceed_review_report` использовать только как финал полноценного ревью. Для мелких проверок отвечать в чат.

## Взаимодействие с пользователем

`ask_user_with_options` использовать для выбора подхода, подтверждения плана и снятия неоднозначности.

## Параллельность

`multi_tool_use.parallel` использовать только для независимых чтений, поисков и проверок.

## Ключевые ограничения

- Не начинать реализацию без подтверждённого подхода.
- Делать только запрошенные изменения.
- Проверять предположения инструментом, а не чтением «на глаз».
- Не добавлять лишние комментарии.
- Отвечать коротко, с результатом в начале.
